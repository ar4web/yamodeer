# HRMS Workflow & Approvals — Requirements Audit

**Source set:** the 20 Markdown guides in `uploads/`  
**Scope:** workflow/approvals first, at the user-selected functional-UI-prototype depth  
**Review basis:** cross-document workflow references, workflow-engine and diagram specifications, business rules/use cases, user/process guides, payroll and integration dependencies, and the existing app's route/RBAC and in-memory operations state.

## Executive summary

The guides describe a broad enterprise workflow platform, but they are a **requirements package, not evidence that those controls or integrations exist in the current app**. They agree on the main capabilities—approval routing, conditions, delegation, SLA monitoring, audit history and notifications—but leave several consequential rules undecided and contain conflicting examples. It would be unsafe to encode those examples as authoritative HR, payroll or financial policy without owner sign-off.

The current app already has illustrative employee-request, transfer, expense and finance records in `OperationsContext`; those are React in-memory state. The client-side role selector and permission matrix are a demo access simulation, not production identity, tenant isolation or authorization. The selected first slice should therefore be explicit about demo boundaries, connect only to local state, and keep unresolved policies configurable/illustrative rather than silently choosing a rule.

## Source-document map

The 20 guides cluster into four useful layers:

1. **Engine and flow requirements:** `ADVANCED_WORKFLOW_ENGINE.md`, `WORKFLOW_DIAGRAMS.md`, `SYSTEM_INTEGRATION_GUIDE.md`.
2. **Business policy and process:** `COMPLETE_BUSINESS_RULES_AND_USE_CASES.md`, `BUSINESS_PROCESS_DOCUMENTATION.md`, `COMPREHENSIVE_PAYROLL_SYSTEM.md`.
3. **Role/task and operational dependencies:** `EMPLOYEE_USER_GUIDE.md`, `GETTING_STARTED_GUIDE.md`, `TROUBLESHOOTING_FAQ.md`, `EMAIL_TEMPLATES_GUIDE.md`, `GOVERNANCE_REPORTING_SYSTEM.md`.
4. **Adjacent functional domains and indexes:** `DOCUMENTATION_INDEX.md`, `USER_GUIDES_INDEX.md`, `USER_GUIDES_COMPLETE_SUMMARY.md`, `GLOBAL_HR_CAPABILITIES.md`, `LMS_USER_GUIDE.md`, `PERFORMANCE_MANAGEMENT_USER_MANUAL.md`, `SKILLS_MANAGEMENT_GUIDE.md`, `STRATEGIC_HR_SYSTEMS_COMPLETE.md`, `TALENT_MANAGEMENT_COMPLETE.md`.

The indexes are helpful navigation aids, but the package needs a policy owner, canonical rule IDs, per-rule source/version, an explicit conflict-resolution process, and testable acceptance criteria. Their coverage/“complete” labels should not be read as validation of every rule or as evidence that the described production controls exist.

## Existing-app baseline and safe first slice

- `OperationsContext` exposes illustrative expense claims, employee requests, transfers and financial workflow records. These are in-memory React state.
- The route and permission matrix is a client-side prototype role simulation; it is not a server authorization boundary.
- There is no workflow persistence, durable audit store, SLA scheduler, live email/SMS transport, or verified approver resolver in this slice.
- The selected prototype adds a bilingual workflow center, unifies supported local employee/transfer/expense queues, allows local approval/rejection, provides a basic workflow-template canvas/editor, local delegation records, visible SLA states/manual escalation logging, local audit/activity, and illustrative analytics/version history. Workflow-specific demo state is kept in this browser tab's session storage when available; shared OperationsContext decisions remain app-memory only. Neither is sent to a server.
- Accounts/payables records are intentionally not presented as approval tasks: their current `PENDING` status represents payment processing, not an approval decision, so a workflow action must not silently convert it to `PAID`. They remain in Accounting.
- Conditional/parallel nodes, approval strategies and routing rules may be configured/displayed, but are not to be misrepresented as a production graph runtime. Workflow state must remain local and clearly identified as a demo.

## Follow-up artifact

The open policy choices are tracked in [`WORKFLOW_POLICY_DECISION_REGISTER.md`](WORKFLOW_POLICY_DECISION_REGISTER.md), with named owner roles and boundary-test requirements for each decision.

## Production-readiness gates (before live approval actions)

1. Obtain signed policy decisions for the payroll threshold, leave routing, expense amount bands, auto-approval cases and return/rework semantics.
2. Define an authoritative identity/tenant/company/department scope and a server-side approver resolver; enforce action authorization and data visibility on the server.
3. Persist immutable workflow/template/step/action records transactionally; pin running instances to template versions; add concurrency/idempotency protection and retry-safe business adapters.
4. Specify SLA calendars, escalation schedules, service/job monitoring, notification delivery/outbox/retry behavior, and audit retention/access rules.
5. Review personal-data minimization, employee-document handling, audit provenance and delegation policy; establish approved integration credentials and vendor/API entitlements independently.
6. Add rule-level acceptance tests and a module-by-module rollout plan; verify each integration in a sandbox before enabling it in production.
